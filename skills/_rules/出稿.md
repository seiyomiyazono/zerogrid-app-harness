## 構造（2026-09-29 本人確定：Sam Piliero式のpack構成）

Metaでキャンペーン／広告セットを分ける相談、新しく作る時は、先にこの節を提示する。出典は承認済みソース Sam Piliero（The Moonlighters）の動画（主張と出典は ad-funnel スキルの references/knowledge/sam-piliero-meta-ads.md）。

```
新規獲得キャンペーン（予算はキャンペーンで自動配分・購入最適化・広め・過去180日の購入者を除外）
├ pack1_<誰に>_<つらさ>  ← 広告セット＝pack
├ pack2_<誰に>_<つらさ>
└ …（新作は毎回、新しいpackで出す。既存packへ足さない）
既存客キャンペーン（小予算・過去180日の購入者だけ）
```

- 新しいpackは7日間だけ「最低消化額＝目標CPA×1」を付け、7日後に外す。最低消化額の合計は全体予算の20%以内。
- 均等予算のテスト用キャンペーン（ABO）・広告単位のクリエイティブテスト機能は使わない。
- 構成は7日間触らない。止めるのは明らかに悪い広告だけ。キャンペーンの作り直しを繰り返さない（「デスループ」）。
- 新作は勝ち広告の核を残した作り直しを中心にする。当たりの定義＝全体予算の5%以上を使って目標ROASを達成した広告。
- アトリビューションは 7日クリック＋1日ビュー＋1日エンゲージビュー（Sam推奨）。旧構成（7日クリックのみ）と数字を比べる時は注意。

- 運用の判断（新作のタイミング・入れ場所・止め時・増額・既存客・毎日見る数字）は ad-funnel スキルの `references/scaling-playbook.md`（Sam Piliero 23本から作成、2026-09-29）に従う。要点：新作は1〜2週ごとに決まった曜日で新しいpackへ／勝ちが出たら作り直しを最低3本／packは基本止めず最低消化を7日で外す／止めるのは目標CPA×2使って購入0か×3使ってCPAが目標より50%以上悪い広告／増額は7日・14日の増分CPAが目標以下なら20〜30%、大きく下回れば50%〜倍、増額後2〜3日は触らない。

### packの分け方＝レイヤーをそろえる

packは **「誰に（アバター）×つらさ」の1段だけ** で分ける。段の違うものを同じ列に並べない（重なって、どのpackに何を入れるかが曖昧になる）。

| 段 | 扱い |
|---|---|
| 誰に（アバター） | packの1段目。互いに重ならない状況で分ける |
| 原因 | 全動画共通の説明。packにしない |
| 起きていること | 全動画共通の場面（冒頭）。packにしない |
| **つらさ** | **packの2段目**。1pack＝つらさ1つ |
| 何を言うか（解決の核） | 全packで共通 |

- つらさの候補は、顧客の実回答（LINE診断「いちばんつらいこと」など同じ段の選択肢）から取り、割合と購入率で優先順位を付ける。
- 名前は `pack番号_誰に_つらさ`（例 pack1_成犬_毎日の床拭きがつらい）。既存広告をpackに入れる時は、その広告の主役のつらさが1つに決まるものだけ。曖昧なものは入れない。
- 着地は、同じ素材の着地別ROASで決める。

## 旧構造（2026-09-14〜09-28。2026-09-29にpack構成へ置き換え）

（旧。今は上の「構造（2026-09-29 本人確定：Sam Piliero式のpack構成）」。分ける相談の時に先に提示するのも上の節。下は 9/14〜9/28 の記録で、アトリビューションも今は上の「7日クリック＋1日ビュー＋1日エンゲージビュー」）

Metaでアドセット／キャンペーンを「分ける」相談が出たら、先にこの節を提示する。ワンドライ等で新しくキャンペーン／アドセットを作る時も同じ雛形で作る（2026-09-14 本人指定）。

```
キャンペーンA「<ブランド>｜本番」 CBO
└ アドセット1つ（ブロード）に勝ち広告だけ。テストの勝者をここへ移す

キャンペーンB「<ブランド>｜テスト｜Tn 変数名」 MetaのA/Bテスト（実験）機能で作成、常に1本ずつ
└ 変数の値ごとにアドセット（同予算ABO・同ターゲット・同素材）。7〜10日、途中編集なし
   T1 着地（記事／PDP直行）→ T2 アングル → T3 フォーマット（VSL／Native／Static）→ T4 アングル別LP
```

- 稼ぐ場所と比べる場所を分ける。本番は統合して学習を溜める（公式：学習完了は1週間に約50結果、「似たアドセットを統合すれば学習も統合される」）。
- 比較はA/Bテスト機能で作る。手動でアドセットをON/OFFして比べない（公式：「informal testing… unreliable」）。1テスト1変数、同予算、最短7日、判定は購入単価とROAS（7日クリック）、片側30〜50購入まで結論を出さない。
- 同じターゲットのアドセットを並べると、公式の「オークション重複」で価値の高い1本しか競らず、予算を使い切れず学習が終わらない。ペルソナ別・ペイン別に分けても比較にはならない（2026-09-09の「ペルソナ×主訴求」分類は、この設計で置き換え。既存セットは本人指示なしに再編しない）。
- アングルは02-顧客分析.mdのペインから定義し（アングルの正本は03-アングル.md）、アングル→フォーマット→アングル別LPの順に1つずつ。同時に掛け算しない。
- 名前は「ブランド｜テスト番号｜変数｜アングル-素材｜値」。テストごとに設計・開始/終了・結果を1枚で記録し、勝ちは本番へ、負けは停止して台帳に理由を残す。
- 予算は本番＋テストで固定し、テスト中は本番の予算も触らない（頻繁な予算変更は学習リセット）。1日15,000円ではどのアドセットも学習が終わらないので、テスト設計の予算は「片側で7〜10日に30購入」から逆算する。
- 既存広告のリンク先・クリエイティブ書き換えは再審査＋学習リセット。テスト用は新しい広告として作る。

## 仕組み（Metaの広告の回り方）

> 2026-09-29注記：この節の「3層の役割」「1人がInstagramを開いた時に起きること」は現役。「だから本番は1アドセット」「比較はA/Bテスト機能」「テストはABO」の部分は、上の「構造（Sam Piliero式のpack構成）」に置き換え済み。

新しいブランドでキャンペーン／アドセットを作る時、広告の分け方を説明する時は、この節の言葉で説明する。

**3層の役割**
- キャンペーン＝財布と目的。「何を目的に、1日いくら使うか」。CBOなら財布はキャンペーンが持ちアドセットへ自動配分、ABOなら各アドセットが財布を持つ。
- アドセット＝誰に・どこで・何を成果にするか。ターゲット、配置、最適化イベント、消化はここで動く。**Metaの学習はアドセット単位**。
- 広告＝実際に見せる中身。アドセット内に複数あると、Metaは人ごとに「一番当たりそうな1本」を選ぶ。

**1人がInstagramを開いた時に起きること**
1. 広告枠が1つ空く。
2. Metaがうちのアドセットの中から「この人に一番当たりそうな広告」を1本だけ選ぶ（広告同士は競らない。Metaが選ぶ）。
3. その1本が他社の広告と競る。勝てば表示。同じ広告主の広告が同じ競りに複数来ると、価値の高い1本だけが出て残りは無視される（公式「オークション重複」）。
4. 買われるたびに、アドセットが「こういう人が買う」と覚える。
5. 最後に大きく触ってから7日以内に約50件で学習が終わり安定する。届かないと「学習が制限」のまま単価が高い。ターゲット変更・広告追加・大きな予算変更でやり直し。

**（旧。今は上のpack構成）だから本番は1アドセット**：同じ相手を狙うアドセットを並べると、手順3で1本しか出ず、手順4の購入が散って学習が終わらない。本番は統合して学習を1か所に集める。
**（旧。今は上のpack構成）だから比較はA/Bテスト機能**：A/Bテストは母集団を切って「Aを見た人はBを見ない」を保証するので、取り合いも早い者勝ちも起きず、変えた1変数の差だけが出る。手動ON/OFFの比較は公式が「信用できない」としている。テストはABO（同額の財布）で公平に回す。

**アドセットに入れる広告の選び方**
- 本番：違う人に当たるものを混ぜる（アングル別に勝ち広告を1〜2本、合計3〜6本。フォーマット混在可）。当たった1〜2本に配信が寄るのは正常。使われない広告は費用ゼロで、当たっている広告が飽きられた時にMetaが自動で次へ移す控えになる。本番の数字からアングルの良し悪しは読めない。
- テスト：変えたい1つ以外は揃える。アングルのテストなら各アドセットにそのアングルの広告だけ、着地のテストなら同じ広告でURLだけ違う。
- 勝ち広告を本番へ移す時は「新しい広告として登録」する（アドセット間の移動はできない）。既存の投稿IDを使い、いいね・コメントを引き継ぐ。広告追加は学習リセットなので、テスト終了ごとにまとめて足す。

**予算の決め方**
- 15,000円はプロダクトテスト（売れる商品か）の基準。すでに売れている商品を新構成に移す時は戻さない。新キャンペーンは予算に関係なく学習ゼロから始まるので、下げても得はない。
- 本番＋テストの合計を固定し、テスト中は本番の予算も触らない。テスト予算は「片側で7〜10日に30購入」から逆算（購入単価×30÷日数×分割数）。
- 本番を上げるのは勝ち広告が揃ってから、少しずつ（運用目安1回2割以内。公式の数値ではない）。

**生き残る広告の判定（過去30日ではなく「最後に大きく触ってからの累計」）**
- 勝ち：ROAS 2以上かつ購入5件以上かつ消化が目標CPAの2倍以上。
- 弱い：消化が目標CPAの2倍以上でROAS 1未満。
- 母数不足：それ未満は判定しない。テストの代表候補か控えにする。

## Static Adsの入稿先と発信元

- 本人が指定した既存キャンペーン・既存アドセットへ入稿する。2026-09-10のスクリーンショットで本人作成の「RT」キャンペーン（In draft）を確認。対象IDと親子関係はブランドの `運用/出稿/設定.md` と実物で照合し、VSLの分類規則を理由に新設・再編しない。未公開の下書きがAPIに出ない場合も「存在しない」と扱って作り直さず、元の下書きを確認できる操作経路を使う。
- Static Adsの発信元はブランド公式Facebookページ（ワンドライ）を使い、VSLで使用する個人名ページを流用しない。公式Page IDの正本はブランドの `運用/出稿/設定.md`。APIでIDとページ名を照合し、作成後の全広告クリエイティブでも `page_id` を確認する。既存VSLの発信元は変更しない。
- 3階層の `status` と `effective_status` を再取得し、「登録済み・子ON／親OFFのため実配信停止」と記録する。子のONだけで配信開始と報告せず、親を自動でONにしない。予算・ターゲット等は指定範囲以外変更しない。

## 入稿前のメディア寸法検収

**全ブランドの新規入稿・広告複製・素材差替えで必須。** 2026-09-09本人指定の再発防止。動画とサムネイルが幅360pxで、Instagramに「500px未満」の警告が出た。720pxは自社の入稿下限であり、全配置の公式最低要件を一律720pxとする意味ではない。

1. **アップロード前**：画像・動画本体・使用するサムネイルの実ファイル寸法を測る。入稿版は横720px以上。動画はffprobe、画像は実画像を開いて測定し、ファイル名やプレビューの表示サイズで判断しない。対象配置の縦横比・尺等も確認し、幅だけで全要件合格としない。
2. **不足なら入稿を止めて修正**：縦横比を保つ配信版を作り、旧版を保全。カット・速度・画角・字幕内容を変えず、全フレームの時刻／尺・音声の保持を検収する。単純拡大で元にない画質が復元したとは扱わない。元の低解像度版を再選択しないようVSL台帳の完成リンクも更新する。
3. **Meta処理後**：video_statusがreadyになるまで待ち、native動画寸法と、実際に広告へ指定するサムネイルをダウンロードして横720px以上を再確認。既存video_idの再利用・広告複製でも省略不可。大きなサムネイルで小さい動画本体の不備を隠さない。
- **2026-09-13本人訂正**：Instagram Stories配信不可を残して入稿完了にしない。今回の管理画面では最小500×889・9:16・60分以内を要求（公式要件は実測時に再確認）。3:4等で警告が出る場合は原本の尺・音声・字幕・画面内容を維持した9:16の配置別版を用意し、他配置へ元動画を割り当てる。API受付・ACTIVEだけで解消済みとせず、警告詳細と反映後の対象配置を実画面で検収する。ヘッドラインの再検討と配置修正は別で、現行維持の指定を引き継ぐ。

4. **広告への反映後**：対象全広告を個別に再取得し、動画ID・サムネイル参照・配置エラーを検査。Facebook・Instagram双方の対象配置のプレビューと警告表示を確認する。APIのプレビュー生成成功だけで警告解消としない。管理画面を確認できない場合は未検収として記録する。
5. **完了報告**：キャンペーン／アドセット／広告のstatusとeffective_statusを確認し、素材修正・審査・配信ON・媒体別の実表示／消化を分けて報告する。配信ONは本人の承認範囲に従い、サイズ修正の指示だけで予算や配置を無断変更しない。本文・リンク・UTM・Pixel・予算の保持、検収日時と証拠をブランドの出稿設定へ残す。

どの入稿経路でも、アップロード前の動画寸法検査と、Meta処理後のnative動画・実サムネイルの寸法検査を行う。新規の定期監視はこのルール保存では登録していない。

## 入稿前の本文チェック

**全ブランドの広告登録・複製・本文差し替えで必須。** 基準は [広告.md「本文の締めは着地に合わせる」](広告.md#本文の締めは着地に合わせる2026-09-28本人指定)。

- Meta APIへ登録する前に、本文と飛び先を下の判定で確かめ、合わなければ送らない。既存の creative_id を使い回す広告も、その本文を読んで確かめる。
- 判定：記事（/pages/advertorial-…）に飛ぶ広告は、本文の最後の2段落に「誰が・何を・記事にまとめたか」が分かる一文（記事／기사／文章を含み25文字以上、「詳しくは記事で」「記事をご覧ください」だけは不可）。商品ページ直行の広告は、本文に記事への言及がないこと。
- 合わなければ本文を直して登録し直す。例外は本人が明示した時だけ。
- 管理画面（ブラウザ）で登録する時も、登録前に本文を同じ判定で確かめる。
