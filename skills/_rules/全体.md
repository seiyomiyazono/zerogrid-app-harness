# 全体ルール — ドロップシップ・ハーネス
更新: 2026-09-07 / 共通基準はこのフォルダが正。商品固有の正本配置は [EC/CLAUDE.md](../CLAUDE.md) に従う。同じ話が2回出たら運営者の後の発言を採用し、関係する正本を更新する。

## 目的
海外で当たっている商品を日本に持ち込み、赤字にならないようROAS 2以上をキープしながらスケールし続ける。
範囲: リサーチ → サイト → 広告(VSL) → 出稿 → 3日テスト判定 → スケール運用(2日ごとに+20%)。

## 進め方の原則
1. 役割を細かく分ける。1エージェント = 1成果物 = 1完了条件。作る役と検品役を分ける
2. 「できました」は証拠にならない。数字・スクショ・URL・機械検査のログを残して初めて合格
3. 使用スキルと作業範囲は最新の本人指定・既存の委任に従う。EC再開は ec-ad-ops（`references/flow.md`）、各工程のスキルは同スキルの案内へ。承認済みの用途を毎回聞き直さない
4. 一気に作らない。1部品ずつ、運営者が把握しながら進める
5. 同時に回す商品は1つ(運営者が指定しない限り)

## Shopifyの複数ストア接続（2026-09-05 運営者指定）
- ストアは追加して保持し、日常作業のたびに接続を切り替えたりリコネクトさせたりしない。別セッションの接続・認証を上書きしない。
- ローカル `shopify-admin` MCPは複数店対応。ワンドライ=`store:otonagi`。毎回の呼出しで対象を明示する。「他店を使用中なので編集できない」と推測せず、各店の `shop_info` で確認する。
- `TOKEN_MISSING` は対象店舗の認証未登録。MCP自体の未接続、Shopify側の権限不足、テーマ編集などのツール未実装を区別して報告する。通常認可で得た有効トークンを対象店の既存秘密envに保存すれば、現行MCPは次の呼出しで読み込む。無断の認証交換・認可拒否の迂回はしない。
- 新しい店は独立した資格情報と固定ドメインの設定を追加して接続検証する。店の追加やツール定義変更時の初回再読込と、普段の店の使い分けを混同しない。
- 実装と接続仕様: `（社内の Mac の道：アプリには無い）`。このMCPの既存6ツールは読み取りと下書き商品の限定編集。テーマ編集は別途対応が必要。

## 工程と承認
```
リサーチ → 【承認① 商品確定を見せる】 → サイト → 広告 → 出稿準備 → 【承認② 出す前に見せる】 → 出稿 → 監視・判定 → スケール
```
- 承認①②以外は全部自動で進める。運営者は細かく見るので、自信を持って自動でやる
- 商品確定後、ブランド名は運営者が指定する。ストア名はそれをもとに決める
- 出稿前に対象ストア・広告アカウント・予算・承認範囲を確認する。既に指定済みなら運用/出稿/設定.mdから読み、未指定の項目だけ本人へ確認する

## 記録と監視
- **広告状況の回答形式**：[判定.md](判定.md)の最新本人指定を読む。ブランドごとに説明を完結する順序・表の列・比較表の扱いを、このファイルへ複製しない。最新取得時刻と期間を示し、実績・基準・助言・仮説を区別する。
- **判定の更新先**：通常の追加・修正指示は基本の[判定.md](判定.md)へ、マーク指定・マーク発言由来の助言は[マーク判定.md](マーク判定.md)へ。基本の期間・停止・増減額を優先し、助言やエージェントの提案で無断上書きしない。一般のデータ分析でも両基準とエージェントの意見を分ける。
- 作業開始時は `EC/台帳.md` と対象自社ブランドのREADME・01-商品情報.md・状態を読む。採用・見送り・ブランド命名が確定したら、同じ作業中に台帳とブランドの記録を更新する。競合元の名前と自社名を区別し、採用によって未検証の研究条件を合格扱いにしない。
- 01-商品情報.md: **商品を扱うたびに `EC/<番号-自社ブランド名>/01-商品情報.md` を作成・更新する**。何を売るか、対象用途、実販売サイズ・色・セット、比較元/セール/メール登録後の全価格・値引額、原価の出所/通貨/送料前提、配送・返品・保証条件、ストアURL、承認日・実反映日・未確認事項をまとめる。VSL/サイト/価格変更の開始時に読む。競合の性能や未確認の見積条件を自商品の確認済み事実にしない。
- 実価格の正本は各ブランドの `01-商品情報.md` だけ。`ハーネス/共通ルール/価格・特典.md` は共通基準と正本への参照を保持し、実価格の横断表を別に管理しない。ユーザーの価格承認とShopify反映完了を区別し、反映後は商品・割引設定・画面・実カートの検収結果を状態.mdから参照できるようにする。
- 状態.md: 商品ごと。現在地・保留・次作業・正本リンクだけを保持する。セッションが切れたらここから再開する。過去経過の追記先にはしない
- 報告.md: 全商品の状況へのリンク入口。数値・進捗は各ブランドの正本だけを更新する。毎朝の報告は運用目標、未登録の定期更新を自動稼働中と報告しない
- 広告の監視: **30分ごと**を運用目標とする。実際の監視登録・稼働状態は各ブランドの状態に記録し、未登録なら自動監視中と報告しない。共通判定基準は [判定.md](判定.md)、商品の判定結果はブランド内の `運用/結果/判定.md`、広告別実績は `運用/結果/日次.md` に記録する
- VSLの正本: 各ブランドの `広告/VSL/台帳.md` に番号・参考競合名・GetHookd広告IDと参考URL（必須）・完成素材・制作状態・Meta配信状態/広告IDを記録する。採用・制作済み・配信中を区別し、本数は最新台帳を参照する。`EC/VSL台帳.md` は入口だけ
- 作業完了前に、台帳・01-商品情報.md・VSL台帳・出稿設定・結果・状態のうち変更に関係する正本を同じ作業で更新し、リンクと実素材を検収する。現在欄を置換し、過去全文は履歴へ保全する。確定方針と実反映は別欄、整理日と観測日は別。詳細な更新契約は[EC/CLAUDE.md](../CLAUDE.md)
- 「また購入」「もう一件」の報告では、Shopifyの最新注文番号・日時・金額・支払い状態を前回確認済み注文と差分照合してから、新規購入を確認したと伝える。既報注文を今回の追加購入と決めつけない。差分を特定できなければ未確認と明示し、必要な注文番号・時刻を確認する（2026-09-06 運営者訂正。旧EC/CLAUDE.mdから移動）。

## 生成（Higgsfield）
旧EC/CLAUDE.mdから2026-09-23に移動。VSL固有の生成・合成の検収は [VSL品質基準.md](VSL品質基準.md#音と費用比較)。

- 生成を伴う制作では、着手前に**使うモデルと消費クレジットを毎回先に伝える**（2026-09-18本人指定）。質を落とさない範囲で必要以上に高いモデルを使わない。クリップは採用窓に合わせて発注し、20秒撮って2秒使うような無駄を出さない。生成原本と編集用カットは毎回 `素材/` の役割別へ振り分け、台帳と検索一覧まで更新してから納品完了とする。
- Higgsfieldの生成が体内の説明カットでNSFW判定になる原因は、赤い描写でも図解であることでもなく、**「ピンク・やわらかい・中空・内壁・体液・マクロで寄る」という語の組み合わせ**（2026-09-19に特定）。臓器名と体の内側を指す語を全廃し、器としての工芸品の語彙（例：壺・注ぎ口・琥珀色の茶・粒・彫り跡）で書く。意味は字幕が運ぶ。**弾かれても同じ文面で投げ直さず、書き直したうえで最短尺の安いジョブ1本で通過を確認してから本番を流す**（本人指定）。NSFW拒否は自動返金されるが、生成スクリプトが落ちると再実行で二重発注になり、その分は戻らない。

## メール・ロゴ
旧EC/CLAUDE.mdから2026-09-23に移動。

- メール・バナー等の自社ロゴは正式な画像資産を使い、通常フォントでブランド名を打った代用ロゴにしない。ワンドライ＝`1-ワンドライ/運用/ウェブサイト/画像/logo-wandry-navy.png`。形状・色・縦横比を保ち、完成画像と照合する（2026-09-07本人訂正）。
- メール画像は本文の最上部にインライン表示し、添付ファイルだけで済ませない。各宛先のブランド・画像実物・割引額を1通ずつ照合し、共通変数を参照する関数で別ブランド画像を流用しない。リンクは発行・注文全体割引の実額検証を終えてから完成と報告する（2026-09-07本人訂正）。
- メール件名は、メール一覧で先頭だけ見えても商品と特典が伝わる順序にし、お礼の言葉で商品名を後ろへ押し出さない（2026-09-07本人訂正）。
