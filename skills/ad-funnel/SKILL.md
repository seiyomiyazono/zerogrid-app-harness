# ad-funnel — 広告の運用分析（判断つき）と数字シート

このスキルは仕組みだけ。ブランドの設定・取得データ・出力は `AD_FUNNEL_HOME`（既定 `（作業フォルダ：アプリには同梱していない見本）`）に置き、スキルには入れない。

## 回し方

```bash
ad-funnel/scripts/run.sh <brand>        # 取得→集計→撮影→シート作成（約1分）
open "${AD_FUNNEL_HOME:-$HOME/ec-ads/ad-funnel}/<brand>/sheet.html"
```

- `<brand>` は `$AD_FUNNEL_HOME/brands/<brand>.json` の名前。どれか分からなければ `brands/` を見て、該当しそうなものを全部回す。
- Clarityは1日10回まで。スキル側で1日8回を上限にして `<brand>/clarity/requests.json` に記録し、上限なら取らずに進む。行を増やしたい時だけ `--clarity 2` のように日数を変えて追加取得する（1回1,000行まで）。
- 個別に回す時: `fetch.py <brand>` → `build.py <brand>` → `node shots.mjs <brand>` → `render.py <brand>`。
- `fetch.py --shop-sessions` で広告ごとのShopifyセッション〜購入（ストア分析と同じ条件、着地URLの `ad_id` で分類）も取れる。今のシートでは使っていない（広告ごとに1クエリでレート制限に当たるため2〜3分かかる）。

## 取るもの（すべて読み取りのみ。広告・サイトの設定は変えない）

| 元 | 中身 | 使い道 |
|---|---|---|
| Meta Marketing API | 広告単位・日別（過去14日＋今日）、昨日と今日の時間別、広告の遷移先URL・画像 | 数字10個・ファネル・日別。「今日」は昨日の同じ時刻までと比べる |
| Shopify ShopifyQL | 購入手続きへ進んだセッションの着地URL（fbclid付き） | 深度ごとの購入率の照合 |
| Clarity Data Export API | URL別（＝クリックごと）のスクロール深度 | 記事LP・商品ページの残存。取得分を貯めて直近8日を合わせる |
| 公開ページ | 記事LP・商品ページのモバイル全長スクショ | 計測タグ（Meta・Clarity・Shopify分析など）を遮断し、`qa_param` を付けて撮る。20時間以内なら撮り直さない |

## シートの決まり（変える時は利用者に確認してから）

- 期間は「今日・昨日・7日・14日」。開いた時は今日。前の期間比は矢印（↗↘ %）で出す。
- 数字は10個：消化・売上・ROAS・購入・CPA／商品ページ到達・CVR・CPM・CPC・CTR。CVR＝購入÷商品ページ到達（Metaピクセル）。
- ファネルは「何%離脱」ではなく「クリックを100%として何%残ったか」（Shopifyのコンバージョン率の内訳と同じ形）。各段の下は、商品ページ＝100%としたカート追加・購入手続き・購入の率だけを出す（クリック・LP表示の段は空ける）。
- 判定・所見・平均比・色での良し悪しは出さない。数字と比較だけ出して、判断は利用者がする。
- 「階層で見る」はカードを並べて押して降りる。「広告ごと」は全広告のカード一覧→押すとその広告の詳細（画像・数字・ファネル・記事/商品ページ・日別）。
- 記事は「そのクリックが実際に着地した記事」で分ける。遷移先を途中で変えた広告は、今の遷移先と実際の着地を並べて注記する。

## 運用分析（判断つき）＝「html分析して」の既定の出力

毎回この順で、同じフォーマットで出す。フォーマット（タブ・並び・判定ルール）を変える時は利用者に確認してから。

### 出力の形（2026-09-28 本人指定・既定）＝広告マネージャ形式
本人の指定：「広告マネージャのデザインを丸ごと写す。オンにしている項目を一つずつ評価し、その下にコメントを全広告で書く。判定は最高・維持・切るで、理由を明確に」。

```bash
python3 ad-funnel/scripts/ops_manager_fetch.py <brand>      # Metaから構成と数字（読み取りのみ）→ ops/manager_raw.json
node ad-funnel/scripts/ops_clarity_heatmap.mjs <brand> /pages/<記事> …   # 記事のスクロール（アプリの専用 Chromeの自分のタブ）→ ops/clarity_heatmap.json
python3 ad-funnel/scripts/ops_manager.py <brand>            # → ops/report.html（前の形式は report_legacy.html）
```
- タブ：広告マネージャ（Campaigns／Ad sets／Ads・期間の切替）／次の動き／記事／判定基準。開いた時は Ad sets・昨日。
- 表の列は本人の広告マネージャの並びと同じ（Off/On・名前・Delivery・Actions・Budget・Amount spent・Impressions・CPM・CTR(link)・CPC(link)・Link clicks・Landing page views・Adds to cart・Checkouts initiated・Purchases・Purchases conversion value・Cost per purchase・Purchase ROAS・Frequency・hook rate true・hold rate）。列名は英語のまま。Actions の列に判定を出す。
- 計算は広告マネージャと一致させる：hook rate true＝3秒再生÷表示、hold rate＝動画の半分まで再生÷3秒再生（実物の値と照合済み）。列や計算が変わっていないか、アプリの専用 Chromeで広告マネージャを開いて確かめる。
- 各広告の下に、項目ごとの評価（EC共通の判定基準 goat・great・good・bad）、いいところ、悪いところ、読み取れること、同じ素材の過去の実績を出す。
- 判定は 最高／維持／切る。理由と「次の条件」を必ず添える。本人が決めたことは `plan.json` の `force_keep`（{広告名: {reason, cond}}）と `force_stop`（{広告名: 理由}）に書き、基準より優先する。
- 記事は着地ごとに、クリック→ページ表示→商品ページ→購入手続き→購入の流れ、弱い段、日ごとの数字、どこまで読まれているか（5%刻み・商品紹介とボタンの位置まで読んだ人）、使っている広告を出す。判定は最高／維持／直す。
- 「次の動き」の先頭は**明日の構成（2026-09-28 本人指定・A案）**：キャンペーンごとに、左＝今ONの構成・右＝次の0:00の構成を同じ行で並べる。種類は 切る（判定が切る・`plan.json` の `tomorrow.off`）／追加（まだ消化0の配信前の広告・`tomorrow.add`）／条件つき（`force_keep`）／そのまま。見出しに本数と日予算の前→後。まだMetaに無い広告を明日入れる時は `tomorrow.add`＝[{camp:"本番|テスト", name, set, dest, why, budget}]、判定とは別に止める時は `tomorrow.off`＝{広告名: 理由} に書く
- 見た目の実測値は `scripts/ops_manager.css`（文字はRoboto 14px、見出し行48px・行46px、名前は#1461cc、罫線#dadcde、縞#f5f6f7、選択タブ#0a78be）。

### 0. 先に聞く（必須）
- **今日何本作れるか**を聞く（記事の修正と新作は同じ作業時間を取り合う。本数は毎回変わる）。答えを `plan.json` の `capacity` に書く。ブランドが複数ありうる時はブランドも聞く。

### 1. 材料をそろえる（すべて読み取りのみ）
```bash
ad-funnel/scripts/run_ops.sh <brand>
```
Meta・Shopify（広告別セッション）・Clarity・記事スクショ → `ops_analyze.py`（判定・`ops.json`）→ 記事の位置の実測とスコア（`ops_articles.mjs`・`ops_articles.py`）→ 新しい動画の取得（`ops_videos.mjs`：統一Chrome CDP 9222 でMetaプレビューを開き mp4 を拾う。自分で開いたタブだけ使って閉じる）→ 文字起こしとキーフレーム（`ops_transcribe.sh`）。

### 2. 分析する（Claudeがやる）
- **判定**は `ops.json` の `ads[].verdict`（自動。下の5つは自動判定の中の言葉で、レポートに出す判定は上の 最高／維持／切る：2026-09-28）。ルール：直近重視（1日ごとに2割引き）、購入が少ない広告はアカウント平均（購入8件分）に寄せた「見込みROAS」。伸ばす＝購入15件以上で確率70%以上／有望＝見込みが目標以上・購入4件以上／維持＝購入15件以上で幅の下限が基本基準以上／入替え＝良く見積もっても目標未満（回したまま、後継が本番入りしたら止める。作り直しではない）／止める＝目標CPAの2倍使って購入0、または良く見積もっても基本基準未満／疲れ＝累計フリークエンシー2.5以上、またはCTR・フック率・クリック後の購入率のうち2つが低下。**ROASの高さだけで「勝ち」と言わない。停止中の昔の数字で引っ張らない**。
- **新しい動画の中身**：`videos/<ad_id>/whisper.srt` とキーフレーム（冒頭0〜3秒）を読み、`creative_analysis.json` に hook／body／cta／good／bad／fix／risk を足す。
- **特徴ごとの比較**：1本ずつでは購入が少ないので、型（長さ・構成）・見た目・着地でまとめて比べる（`plan.json` の `evidence`）。帯が重なるものは「差があるとは言えない」と書く。
- **着地**：広告ごとの記事→商品ページ率・クリック→購入。絵や動画と記事の話がつながっているかを見る。**既存の広告のリンク先は変えない**（学習がやり直しになる）。変えたい時は、着地を試す別の pack として出す（`references/scaling-playbook.md` ②。着地だけ変えた出し直しはしない）。
- **記事のスコア**（`ops_articles.mjs`→`ops_articles.py`、`article_score.json`）：記事は「読まれて」「読むと買う」から意味がある。
  - 読まれる：商品紹介（商品名が最初に出る位置）まで届く率 ≥30% A／20〜30% B／<20% C（友達の参考値「良い記事は最後まで3割」。購入ボタンで途中から商品ページへ移る人が多いので、ここでは商品紹介で見る）
  - 効く：商品紹介まで読んだ人の購入率÷読まなかった人 ≥2倍 A／1.3〜2倍 B／<1.3倍 C（購入8件未満はデータ不足）
  - 判定：効くがC → **商品ページ直行を別の pack で出して比べる**（記事が購入率を上げていないなら直行の方が良い）／効くがA・B で読まれるがB・C → 読まれ方を直す（商品紹介を前へ・紹介の直後に購入ボタン・1画面目に結論）／両方A → そのまま、伸ばす所だけ／100人以上で購入0 → 使わない
  - 動画とのつながり：広告ごとの「1画面目で帰る率」が記事の平均より5ポイント以上悪い＝動画の約束と記事の冒頭がずれている。直し方に、どの動画から来る人向けに冒頭をどう変えるかまで書く
  - 直し方は「どこ（位置%）を・どう変えて・何%を何%にしたいか」まで具体的に。新作の着地は、同じ骨組みの広告が一番読まれた記事にする

### 今の構成の数字だけで決める（2026-09-28 本人指定。下の9/27の鉄則より優先）
- 判定には `current_since`（キャンペーンを組み替えた日）からの数字だけを使う。前の構成・前の記事で良かった実績は使わない。今の構成でうまくいっていない広告は本番に入れない。
- 見るのは常に「今日・昨日・今の構成の累計」。取得は `ops_manager_fetch.py <brand> <current_since>`。
- （旧運用。2026-09-29 から使わない：下の「構成の前提」）テストは 1セット＝1本・1日¥10,000・目的を1つ決める。2日かつ目標CPAの2倍に届いたら、購入3件以上・ROAS 3以上で**昇格**（本番へ複製し、テストのセットは止める）、購入0かROAS 2未満で切る、その間は1日だけ延長。CTR・フック率・維持率も一緒に見る。
- 本番は、購入0で目標CPAの2倍・ROAS 1未満・目標CPAの4倍使ってROAS 2未満のどれかで切る。昇格した素材と同じ素材の別版は入れ替える。
- 判定は `ops_manager.py` の `judge()`。前の判定は `judge_old()` に残してある。

### 切る・残すの鉄則（2026-09-27 本人訂正）
- 切る提案は、必ず判定基準と過去の実績に当てはめてから出す。**今日の少ない消化だけで切らない。「本数を絞るため」は切る理由にしない。**
- 同じ素材は、広告を作り直していても過去の広告と合算して判定する（今日を含める）。`<brand>/reanalysis/creative_verdict.py` が素材ごとの累計・直近重視のROASと幅・最後の購入からの消化を出す。
- 止めるのは次のどれかに当てはまる時だけ：①購入0のまま目標CPAの2倍を使った ②最後の購入から目標CPAの2倍を使って購入0で、直近重視の購入が5件未満 ③良く見積もっても基本基準未満 ④判定が入替えで、後継が本番に入った。
- テストも同じ。1日¥1万前後の消化で購入0でも、目標CPAの2倍に届くまでは続ける。
- 本人が毎回確認し直さなくて済むよう、切る・残す・入れるの各行に「判定」と「根拠の数字」を必ず添える。
- 着地は案件の方針に従う。成績が悪い時は、旧記事へ戻す提案より先に新しい記事の直しを考える。

### 構成の前提（2026-09-29）
Metaの構成・新作の割り当ては EC共通ルールの出稿.md「構造（Sam Piliero式のpack構成）」と「packの分け方」に従う。旧来の「1セット1本・各¥10,000のABOテスト」は使わない。以下の test_schedule の記述は旧運用。

### 3. `plan.json` を書く（型は `assets/plan.example.json`）
- 新作（`briefs`）は **capacity の本数ちょうど**。1案＝1本。骨組みは根拠の厚い型、変えるのは冒頭・見た目・悩み。参考（`ref`）は既存の広告名、着地（`dest`）と理由も書く。入り切らない案は `later` に。
- （旧運用。2026-09-29 から使わない：上の「構成の前提」）テスト（`test_schedule`）：**1セット＝1本**。今日作るものは**全部明日0:00に入れる**（テストは本番と別予算のABOなので本番を崩さない）。1日目は反応（フック率・CTR・カート）で振り落とし、残りに予算を寄せて3日で判定。再テスト（`retest`）は、有望なのに本番（CBO）で予算が回っていない広告。
- 記事の直し（`article_fixes`）：今日やる分に「今日」、残りは「次」。本数と作業時間を合わせる。
- 本番は今のメインキャンペーンをそのまま使う（新作は入れない）。
- 追加のキー（2026-09-26）：`keep`＝様子見・購入5件未満でも本番に残す広告名の配列（購入が付き始めた広告など）／再テスト項目の `to`＝着地を変える時の表示（例「記事02-new」）／`capacity.made`＝制作済みの新作本数（手順が「視聴して出稿へ」になる）／`extra_steps`＝[[見出し,本文]]で「今日やること」の末尾に手順を足す／`decision`＝{title, cap, points[[見出し,本文]], sources[[名前,URL]]}で「決めたこと」カードを「明日の構成」の先頭に出す（本番を新規にするか等、根拠と出典つきの判断）。
- 配信開始後（`launched: true`）の追加キー：`force_keep`（{広告名: 理由}。自動判定が「止める」でも本人指定で本番に残す。警告は「判定待ち」と表示）／`test_schedule` の項目 `new_ad`（制作済みで未登録の広告名。`set`・`ref`・`why` を添える）／`stop_head`・`stop_notes`（止めるセットの理由）。開始済みの広告は期間の実績が無いので今日の数字を表に出す。`ops_render.py` は Python 3.12以上で実行する
- `w_registry`＝広告名のW番号の台帳（`map`：素材名→番号、`next`）。レポートの自動採番（W101〜）は初回だけで、以後はこの台帳を正にする。同じ素材の複製は同じW、着地コードだけ変える。
- `ops/articles_new.json`（任意）：Shopify照合が取れない日や流入が今日だけの記事は、Metaピクセルの経路（記事表示→商品PG→カート→購入手続き→購入）とClarityのURL別集計でカードを作り、記事タブの先頭に出す（cards[].today/old/clarity/ads、reference）。作り方は 2026-09-27 の wandry/reanalysis を参照。
- 本番を新規キャンペーンにするかは毎回同じ結論にしない。学習は広告セット単位（公式）なので、既存セットの学習状態（`structure.json` の `learning_stage_info`）と週間購入を見て判断し、`decision` に出典つきで書く。

### 5. チャットでの報告
見出しと表で短く：判定の表（見込みROAS・今の数字・購入・明日どうするか）→ 明日の構成（本番／テスト／止める）→ 今日やること。**広告の停止・複製・予算変更・記事の変更は実行前に必ず確認**（ここでは何も変えない）。

## 報告のしかた（数字だけのシート）

- シートのパスを渡し、取得時刻・Clarityの対象期間とクリック数・照合件数を一言添える。
- 「良い/悪い」の判定や停止・増額の提案は、聞かれない限りしない。
- 計測の食い違いを見つけたら数字を添えて事実として伝え、原因は確かめた範囲だけ言う。
  - 例: 記事をストア外（Vercelなど）に置いている広告は、ストアの計測でLP表示が少なく出る。クリックとLP表示の差をそのまま「離脱」と言わない。

## 限界（毎回そのまま伝える）

- 深度はClarityのサンプル。1回1,000行の上限があり、日付でも区切れないため、深度の欄は期間切替の対象外。
- 購入率の照合は fbclid が両方に残っているクリックだけ。
- 遷移先がMetaから取れない広告（古い形式）は、Clarityで実際に着地したページで補う。
- Metaの数字（LP表示・カート・購入）とShopifyのストア分析の数字は定義が違うので少しずれる。

## ブランドを足す

`assets/brand.example.json` をコピーして `$AD_FUNNEL_HOME/brands/<brand>.json` を作る。秘密の値は書かず、`（鍵はアプリの接続で管理）`（`AD_FUNNEL_SECRETS` で変更可）にある秘密ファイルの名前と変数名だけを書く。初回セットアップは `README.md`。
