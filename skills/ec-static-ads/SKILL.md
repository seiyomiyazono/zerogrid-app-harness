# 自分で作る静止画（標準。2026-10-07 運営者 合格「これを static ads の10このフォーマットとしてハーネス組み込んで」）

正本：`ec-ad-ops/references/static-formats.md`。ここは入口の要約で、食い違ったら正本が先。

1. **商品のマークダウンを読む（必ず）**：`<商品名>/` の `04_初日の出稿設計.md`（どの pack・着地）→ `05_原稿の決まり.md`（呼び名・根本原因の名前・ヴィラン・言ってよい事実）→ `01_商品理解の基盤/` の `H_根本原因.md`・`I_仕組みの細部.md`（あれば）・`B_市場と悩みの地図.md` の原文・`A_商品の事実.md`・`E_強みと唯一性.md`・`F_刺さる層とpack候補.md` → `06_原稿/` の同じ pack の原稿。どこに何を使うかは正本の2.5章の表。`H_根本原因.md` が無ければ作り始めない。読んだファイルと使った原文の番号を、原稿の頭に書く
2. **型を選ぶ**：st01 実体化／st02 フィギュア／st03 体内ツアー／st04 ミニチュア職人／st05 彫刻の比較／st06 時刻のコマ割り／st07 クレイの世界＋商品／st08 マスコット化／st09 体に手書き／st10 メッセージ画面。1つの pack で2〜4型を変えて出す（入口・根本原因・ヴィランは同じ）。広告の名前に型の id を入れる
3. **画像**：絵の案を1行で書く（「何を、どんなありえない絵に置きかえるか」）→ プロンプト（ひな形 `ec-ad-ops/templates/static-formats/`）→ **Codex 内蔵の imagegen**（`codex exec … < /dev/null`）。商品が写る型は実物の写真を参照に渡す。4:5
4. **ヘッドラインと本文**：画像1枚ごとに、見出し（27字以内）と本文3案（短い・中くらい・長い）。決まりは `ec-ad-ops/references/creative-foundation.md` の6章。画像の文字と同じ事を、見出し・本文の頭でくり返さない
5. **点検**：正本の5章（文字を1字ずつ・1秒で分かるか・05 と同じ言葉か・商品は実物と並べる）
6. **納品**：`<商品名>/07_納品/Static Ads/<pack の名前>/<広告の key>_<型の id>_<題名>/` に `画像.png`・`ヘッドライン.txt`・`本文.txt`。原稿は `06_原稿/`。Meta への登録は 運営者 の承認の後、停止で

採用された参考画像の構図と広告文を保ち、日本語の掲載セットを作る。素材取得・翻訳・画像生成・独立検品はエージェントが実行し、同梱スクリプトは納品ファイルの機械検査を担当する。広告管理画面への出稿を自動実行するスキルではない。

# 開始と素材取得

1. ECハーネスがある案件ではその入口から対象ブランドの `01-商品情報.md`、`状態.md`、`広告/Static Ads/台帳.md` と最新の本人指定を読む。新規案件なら対象ブランド、販売中の商品と条件、参考広告、出力先を既存情報から埋める。価格・本数・特定広告IDをこのスキルへ固定しない。
2. 選定済みの参考広告は選び直さない。未選定なら依頼されたブランドと静止画形式を確認し、指定された星評価・スコア・稼働期間で候補を絞って実画像を検品する。GetHookdの評価は競合のROASやリターゲティング配信対象を証明しない。取得日時と表示値を残す。
3. 正式な利用可能経路で元広告の画像本体を取得する。GetHookdカードやブラウザUIのスクリーンショットを広告画像の代わりにしない。元画像を実際に開き、サイズ・比率・文字・商品・構図を確認する。
4. 元広告の **広告見出しと投稿本文を別々に取得し、全文保存** する。画像内文字のOCRは画像翻訳の補助であり、広告見出し/投稿本文の代用ではない。元見出しが無い・取れない時は制作資料と台帳に補完案と記録する。元本文が取れない時は未取得と記録し、全文翻訳済みと呼ばない。

# 参考広告の分析（2026-09-21本人訂正）

制作前に、元画像で最初に目を止める物体・質感・異変、その異変が表す具体的な痛み、商品による解決の見せ方、画像/見出し/本文の対応を分解する。配色・文字組・段落数の一致だけで「参考を再現した」としない。視覚的比喩が核なら、普通の生活写真への置換でその核を落とさない。別商品への参考制作では、何を何に変形し、どの感覚を伝え、商品へどうつなぐかを1案に落としてから生成する。単なる日本語化の依頼では勝手に新しい比喩へ変更しない。

広告成果の原因は実績や比較なしに確定しない。元画像で観察できる表現と、なぜ効くと考えるかの仮説を分ける。独立検品は文字/商品条件に加え、異変が主役か、悩みが説明なしでも読めるか、商品と解決の対応があるかを確認する。文字化けなし・整った画像だけを企画品質の合格にしない。本人の却下後は旧合格を完成判定へ流用せず、却下理由と旧版を保全して見直す。

# 翻訳と自社条件への置換

- 画像内文字と掲載文の意味・順序・訴求を保つ。勝手な要約、別アングルへの変更、原文にない体験談やレビューを足さない。日本語は読みやすい言い回しにし、文字枠へ収まるよう改行を調整する。
- ブランド、商品、価格、割引、枚数、保証、リンクを現行の商品データと照合する。本人確定だがサイト未反映の価格版を公開広告へ先行適用しない。登録限定特典を全員対象と書かない。置換前→置換後、根拠ファイル/確認日、使用する価格版を制作資料に記録する。
- 元広告のレビュー・体験談・性能比較の数字は、ユーザーの忠実翻訳指定に従って原文のまま日本語化する。自社の未検証を理由に自動削除・一般化しない。
- 「今夜終了」「ラストチャンス」等の期限・特典条件はオファーとして現行条件へ合わせる。実際の締切がないのに競合の締切を自社の本日限定へ流用しない。本人の最新指定が既定手順より優先する。
- 「元広告によると」等の制作事情や確認メモを掲載文・画像に足さない。由来の説明は制作資料へ分離し、顧客向けの警告コピーで広告を作り変えない。
- 商品の形状・販売する種類・セット内容が参考と異なる場合は自社の商品資料と照合する。正式ロゴを使う指定では正式画像資産を添付し、通常フォントのブランド名でロゴを代用しない。

# 画像生成

生成の接続・パラメータ確認には利用可能な `higgsfield-generate` Skillを読む。この工程は **Higgsfield CLIのGPT Image 2、モデルID `gpt_image_2`** を使う。参考画像付き広告でも別の画像モデル・Marketing Studio・別サービスへ自動で切り替えない。

1. `higgsfield account status` と現行モデル一覧/`higgsfield model get gpt_image_2 --json` で接続・入力仕様を確認する。未認証・生成制限・課金エラー時は素材/翻訳など独立作業を終え、止まった生成と理由を明記する。モデル変更にはユーザーの指定が必要。
2. **採用した元広告画像そのものを `--image` へ渡す。** プロンプトだけで似た構図を新作したり、画像の説明文だけをリファレンスと呼んだりしない。複数画像が必要なら仕様確認のうえ元広告・自社商品・正式ロゴの役割を明示する。
3. 元の比率、レイアウト、配色、写真の被写体/配置、比較欄、付箋、星、文字の階層を保持する。日本語訳と必要な自社条件の置換だけを指示する。写真部分を独自の演出へ変えない。元と同じ比率を基本に、媒体の必要画素数を満たす品質で生成し、実寸を検査する。
4. プロンプトはUTF-8ファイルへ保存し、画像内全文の置換表を含める。CLIの現行仕様に従って読み渡す。例：

```bash
higgsfield generate create gpt_image_2 \
  --image "$STATIC_SOURCE_IMAGE" \
  --prompt "$(cat "$STATIC_PROMPT_FILE")" \
  --aspect_ratio "$STATIC_ASPECT_RATIO" --resolution 2k \
  --wait --json > "$STATIC_GENERATION_RECORD"
```

シェル変数には案件側の実パス/比率を設定する。生成レスポンスは制作資料へ保存し、成功した実画像をダウンロードして開く。元画像hash、渡した参照画像、model、job ID、結果URL、パラメータ、生成日時、完成hashを記録する。タイムアウトでは既存jobの状態を再確認してから再生成し、二重発注を避ける。修正は同じGPT Image 2で不合格箇所を具体的に指示し、失敗版を完成扱いにしない。

# 納品

VSLと同じく1番号が1掲載セット。Static Adsの番号はそのブランドの同形式台帳の続きとし、VSL番号を消費しない。

```text
<ブランド>/広告/Static Ads/
  台帳.md
  01/
    01-image.png
    ヘッドライン.txt
    本文.txt
  _制作資料/01/
    （元画像・出所/原文・翻訳置換・プロンプト・生成記録・検収）
  _過去版/01/<日時>/
    （修正前の掲載セットと対応する制作資料）
```

- 完成PNGは実PNGへ保存する。拡張子だけを変えない。掲載フォルダへ元画像・中間案・説明書を混ぜない。修正前のセットと資料は過去版へ保全し、既存完成を無記録で上書きしない。
- `ヘッドライン.txt` と `本文.txt` は管理画面へ貼る日本語文だけ。見出しラベル、元広告ID、出所URL、制作注記を入れない。原文にある購入リンクは自社の確認済み着地へ置換する。
- 台帳は番号、参考競合、元広告ID、完全なshare URL、画像/ヘッドライン/本文への相対リンク、訴求、着地、使用価格版、制作状態、公開保留理由、Meta配信状態/広告ID、検収資料リンクを持つ。採用・生成済み・検収済み・出稿済みを分ける。元データ/生成記録の書式は案件に合わせ、既存資料があれば再利用する。
- 今回変更した台帳とブランド状態を更新する。商品条件・出稿設定を変えていなければ数値を複製せず参照する。配布スキル内へ実素材・顧客情報・資格情報・個人用案件設定を収録しない。

# 検収と完了

制作と検品を分け、ECハーネスの指定に従い利用可能な別担当へ元画像・訳文・商品データ・完成画像を渡す。別担当を使えない時は別パス検品と明記し、独立検品済みと呼ばない。

- 全番号の元画像と完成画像を実表示して、構図、文字の抜け/化け/英語残り、価格、条件、ブランド、ロゴ、商品形状を比較する。OCRだけで目視合格にしない。原見出し・原本文と納品テキストをそれぞれ照合する。
- 画像生成の入力記録で元広告が実際に参照され、modelが `gpt_image_2` であることを確認する。成功レスポンスだけで画質/翻訳合格にしない。
- 次の機械検査でファイル数・PNG破損・寸法・文字ファイル・資料/台帳リンクを確認する。Pillowが必要。画素下限は案件/配置の規格から指定し、元の比率を無理に正方形へ変えない。

```bash
python3 scripts/validate_delivery.py "/path/to/ブランド/広告/Static Ads" \
  --ids 01 02 --min-width 1080 --min-height 1080
```

この検査は意味の正しさ、性能根拠、Meta処理後の品質や配信状態を保証しない。生成失敗・誤訳・条件不一致など実際に残る不備は番号ごとに明記し、未完成を完成と呼ばない。原文にあるレビュー/性能数字の由来記録は、追加承認や出稿ブロックの条件にしない。広告入稿の依頼がある場合はECの出稿規格で実素材と媒体側の処理結果を検収し、既存の出稿承認範囲に従う。通常の制作依頼では掲載セットの納品リンクまでを返す。

# オリジナル静止画（参考の翻訳ではなく、こちらで作る時）—

> **2026-10-07 運営者 指定**：自分で作る静止画は、①型の番号と名前（st01〜）を持ち、pack の中で型を変えてテストする ②**画像は Codex 内蔵の imagegen で作る**。型の一覧・呼び方・点検は `ec-ad-ops/references/static-formats.md`。下の見出しが主役の型は、その中の1つとして残す。

見出しが主役の型（上の指定のとおり、型の1つとして使う。毎回この型に固定しない）。
- **型**：4:5（1080×1350）。左上に正式ロゴ／大きな装飾見出し（明朝・強調語を大きく赤）／小さなサブコピー／丸バッジ3つ（2行・強調語を赤）／右に専門家の人物写真（記事の語り手と同じ人物・切り抜き）／手前に商品写真／人物の横に帯（肩書き＋「が解説」）と名前／一番下に全幅のボタン帯（「◯◯を記事でチェック！ ▶」、商品ページなら「今すぐチェック！ ▶」）／右下に「※イメージ」
- **色**：ブランドのロゴの色に合わせる
- **作り方**：Codex 内蔵の imagegen に、デザインの参考画像・人物の写真・商品写真・正式ロゴを参照で渡し、画像内の文字を全部「この文字だけ」と指定する
- **確認**：拡大して1字ずつ見る（見出し・バッジ・帯・名前・ボタン・※イメージ）。人物の顔が渡した写真と同じか。誤字があれば同じモデルで直す
- **納品**：画像・ヘッドライン.txt・本文.txt（本文の締めは「ぜひ下のリンクから…」「あなたも今日で、◯◯を卒業しましょう」）。運用ボードの動画タブにも載せる
- 文字だけを並べた画像（デザインのない画像）は作らない
