# ec-research をアプリの中で回す（読み替えの表）

アプリ（Zero Grid）では、社内の Mac の道具（Google スプレッドシートの台帳・`scripts/*.mjs`・`data/`・Agent の並列・Artifact）が使えない。
**探し方は `アプリでの探し方.md` が正**（2026-11-03。刺さるか・高く見える質か・原価の安さの3つで、点数は付けない。商品を先に見つけ、競合は後で探す。SKILL.md の全件列挙・広告の本数・80点は使わない）。この表は、**道具と置き場**の読み替えだけ。

## 1. 読み替えの表

| 手順書に書いてある物 | アプリでは |
|---|---|
| `scripts/sheet.mjs doctor` → `keys`（Phase 0。調べ済みを外す） | zg の `ledger_check`（keys を渡さない＝全部の行）。気になる key だけ聞く時は `ledger_check {keys:[…]}` |
| 深掘りの前（Phase 4 に入る前） | 深掘りする候補を `ledger_check {keys:[…], candidates:[{name, category, urls, ids}]}` で聞く。この店で調べ済み（`見送り`・`確定`）は深掘りしない（`再調査可`・`保留` で条件がそろった物は深掘りしてよい）。**中央で exclude:true の候補は、ほかの店が使っている商品なので必ず外す**。dead_end（ほかの店が見送った理由と数）は参考にする |
| `scripts/sheet.mjs upsert '<JSON>'`（Phase 7） | 調べた候補は**1つ調べ終わるたびに** `ledger_record {entries:[…]}`（`key`・`niche`・`product`・`score`・`verdict`・`note`〈見送りは理由が必須〉・`dropship`・`sourcing`・`competitors`・`market`・`report`）。最後にまとめて書くのではなく、その場で書く（途中で止まっても調べ済みが残る）。見送りには中央へ出す理由の札 `reason` も1つ付ける |
| 確定（3つの候補から使う人が選んだ1つ） | 決めてほしい事のカード（kind decide）で「この商品で行きますか」と聞き、行くと言われたら `ledger_claim {key, name, category, urls, ids, product}`。status が `taken` なら、ほかの店が先に決めた商品なので、その商品では進めず、次の候補に移る |
| `scripts/sheet.mjs obs`・`scripts/track.mjs <domain…> --browser --json` | zg の `research_stores`（`domains` に店のドメイン、`ads` に `{ドメイン: 広告の本数}`、定点観測は `observe:true`）。SimilarWeb は取らないので、決勝の3〜5社だけ WebFetch（`references/data-sources.md` の訪問数カスケード） |
| `products.json` の `body_html`・商品画像を見る（Phase 3・discipline 1） | `research_stores` の返り（上の5商品の名前・選ぶ物・説明の頭・写真）。足りなければ WebFetch で `https://<店>/products.json` |
| Phase 2 の機械足切り（サイズ選択・商品数） | `research_stores {deep:false}`（products.json だけ・速い）の `sizedRatio`（サイズで選ぶ商品の割合）・`productCount`・`priceMin/Max` |
| `data/banger-index.json`（貯める・次は差分だけ） | zg の `research_index`（`entries:[{pageId, nm, dom, ads, at}]` で足す。書かずに呼ぶと今の一覧）。置き場はワークスペースの `research/banger-index.json` |
| `data/store-gate.json` | `research_stores` が `research/store-gate.json` に自動で貯める（同じ日は測り直さない） |
| そのほか、商品が決まる前の下書き（候補の表・クラスタのメモ） | `write_file` の `research/<名前>.md`（`.json`・`.csv` も可。上書きする。1MB まで）。Read でも読める |
| `mcp__gethookd__search_ads` などの GetHookd の道具 | zg の `gethookd_search_ads`・`gethookd_search_brands`・`gethookd_list_shops`・`gethookd_get_brand`・`gethookd_get_top_ads` …（読むだけの物。`connected` で GetHookd がつながっているか先に見る）。返事は1回6万字で切れるので `limit` は 20 以下 |
| `transcribe_ad`（VSL の文字起こし） | 使えない（新しく頼む道具は入れていない）。`search_ads` の返りの `transcripts` を使い、無ければ「取得できず」 |
| ToolSearch でスキーマを読む | 要らない（zg の道具は最初から見える） |
| Agent ツールで並列に深掘り（Phase 4） | 使えない。クラスタを1つずつ、同じ手順で順に深掘りする。長くなる時は返事の `next`（同じダルマ）で続きを頼む |
| Meta 広告ライブラリ・SimilarWeb・楽天・Alibaba・CJ を見る | WebFetch（JS が要るページは落ちやすい → WebSearch で補い、取れなかった物は「手動確認ポイント」） |
| python3 で JSON を読む | 使えない。道具の返りを直接読む（大きい物は件数を絞る） |
| Artifact を1枚発行（Phase 6）・artifact-design | 使わない。下の 2 のとおり、商品フォルダに HTML を置く |
| `references/knowledge/…`（プレイブック本体）・社内の作業フォルダ | アプリには無い。手順書と references だけで回す |
| 「ブラウザで1社ずつ開く」 | アプリでは自分で操作しない（GetHookd と WebFetch で取る） |

台帳は2段。この店の詳しい台帳（ワークスペースの `research/ledger.json`。手順書の列そのまま。理由の文もここだけ）と、Zero Grid の中央の台帳（全部の店で共通。出るのは指紋と札だけで、名前・理由の文・だれかは出ない）。道具は同じ1つの口で両方に書く。中央につながっていない・同意が無い時は、この店の台帳だけ。

## 2. 商品が決まった時（Phase 5〜7 の順番）

商品フォルダを作る・報告を置く（product_start・write_file）のは、ファイルを作ってよいダルマ（商品ダルマ）。ファイルを作れないダルマ（分析ダルマ）で調べていた時は、ledger_claim までして、返事の `next` で商品ダルマ（id `product`）に「<key> で確定。商品フォルダを作って報告を置く」と引き継ぐ（調べた中身は research/ と台帳に残っている）。

1. 決めてほしい事のカードで「この商品で行きますか」と聞き、行くと言われたら `ledger_claim {key, name, category, urls, ids}`（status が `taken` なら、その商品はやめて次の候補へ）
2. zg の `product_start {name:"<商品の呼び名>"}` で商品フォルダを作る（承認は要らない。同じ名前があればそれを使う）
3. `write_file` で次を保存する
   - `<商品>/00_リサーチ/参入パック.html` … `references/report-template.html` の `{{ }}` を実データで埋めた1枚（埋まらない枠は「取得できず＋理由」を赤字）。外の画像は使わず、リンク（競合のサイト・広告の share_url）だけ
   - `<商品>/00_リサーチ/リサーチの結論.md` … 結論（1商品）・ドロップシップ判定・市場規模・競合（実物1行つき）・参入コンセプト・参考広告・ネクストアクション（SKILL.md の「出力ルール」の順）
   - `<商品>/00_入口.md` の表（商品名・何をする商品か・売値の案・仕入れ先の URL と原価・届く日数）。分かっていない欄は空のまま
   - `<商品>/01_商品理解の基盤/` の分かっている所（C_競合の地図.md の売り手の表＝同じ商品の競合・価格・主な主張・出典の URL、B の悩みの原文があればそこ）。推測で埋めない
4. `ledger_record` で確定の行を直す（`verdict:"確定"`・`report:"<商品>/00_リサーチ/参入パック.html"`）。見送った候補も全部書いてあるか確かめる
5. 返事：`attach` に `<商品>/00_リサーチ/参入パック.html` を入れる（画面で開ける。店 > 商品の「この商品で決めた物」の「リサーチの報告」からも開ける）。
   `next` に商品ダルマ（id `product`）で「<商品> の商品理解の基盤（ec-ad-ops 工程1）を作る」を書いて引き継ぐ

## 3. 3つとも「はい」の物が見つからない時

確定にしない（`ledger_claim` は呼ばない・商品フォルダは作らない）。調べた候補を全部 `ledger_record`（`見送り`＋理由、`保留`＋条件）に書き、「まだ見つかっていない。次はここを掘る」と報告する（`discipline.md` 7）。
