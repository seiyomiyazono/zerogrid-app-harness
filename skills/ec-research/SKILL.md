# ec-research v6 — DTC商品リサーチ（全件列挙・同一商品の実証・1商品だけ返す）

> **アプリで回す時**は、この手順書の探し方（全件列挙・広告の本数・点数・80点）は使わない。同じフォルダの `アプリでの探し方.md`（2026-11-03：刺さるか・高く見える質か・原価の安さの3つ。商品を先に見つけ、競合は後で探す）が正。台帳・置き場・道具の名前の読み替えは `アプリでの回し方.md`。

## 思想

> 参入候補 = **ドロップシップで作れる** × 海外の**ドロップシップ勢**が広告費をかけて実証済み × 日本ではまだ空白 × 薬機法をクリアできる × 市場がデカい

- **winning productは存在しない**（成功=Product×Creatives×Funnelでproductの寄与~20%）。終点は「商品」ではなく**「商品+参入コンセプト」**
- **マージン2ルール**（3x COGS+粗利$25〜30）は参考（2026-10-18：利益率は判定に使わない）
- **「今すぐ痛い」問題のみ**
- 実証の主指標は**アクティブ広告本数**。訪問数は補助証拠

## v6の変更（2026-08-20・運営者の監査由来。**ここが最優先**）

1. **探す段階でキーワードを使わない → 全件列挙**（`references/enumeration.md`）
   サブニッチ生成とキーワード掃引を廃止。Hookdで「広告1,000本以上×Shopify＝**538社**」を全件取ってから絞る。
   キーワードで引くと**引かなかった語の外にある商品が構造的に見つからない**（実例: 耳栓を自分のリストに入れながら取りこぼした）
2. **DS判定を「ストアの商品数」から「主力商品への広告集中度」に変更**（`references/dropship-check.md` A0）
   商品数で捨てると Vion（39商品・広告3,271本が1商品に集中）を落とす
3. **競合は実物を見てから載せる**（`references/discipline.md` 1）。商品名から推測して競合表に書くのは禁止
4. **運用規律を明文化**（`references/discipline.md`）。証拠の格付けを案件で変えない／市場規模は買う人の数で数える／
   スクレイパーは1件で検証してから全件／並列8タブ／測ったものは保存／必須を満たさない商品は運営者に出さない

## v5から継続する原則

- **同一商品ルール**（`references/same-product-rule.md`）。課題が同じでも商品が違う競合は実証に数えない。電動と非電動、クリームと器具は別商品。OEM差までが同一。**同一商品のDS型3社未満は足切り**
- **点数は候補出しの参考**（2026-10-18：点数は付けず、確定は下の「運営者 の最新の決まり」の必須7つ。前の合格ライン80点は使わない）
- **advertorialを回していたらDS型確定**として扱う（自社ブランドはこの型を使わない）
- レポートは `references/report-requirements.md` の5ブロック必須: **競合サイト3 / native ads 3 / advertorial 3 / VSL 3 / 広告アカウントTop3**
- **指標と売上逆算は `references/metrics.md` が正**
- **調査済みの正は台帳**（アプリでは zg の ledger_check・ledger_record。中央の台帳がつながっていれば中央、無ければワークスペースの research/ledger.json）。載っていないものは未調査（運営者が行を消す＝再調査可の意思表示）
- **返すのは1位の1商品だけ**（並べ方はアングルの多さ）。ランキングページは作らない

ニッチ前提: 健康・美容の悩み系。ファネル前提: Shopify + Meta広告（VSL/アドバトリアル→LP）。
プレイブック本体はアプリには同梱していない（この手順書と references だけで回す）。

## フロー

### Phase 0: 台帳同期＋規律の読み込み（毎回・最初に必ず）

1. `references/discipline.md` を読む。**8項目の縛りを頭に入れてから作業を始める**
2. zg の ledger_check（keys を渡さない）で調べ済みの一覧を取り、除外セットを作る（`references/ledger.md`）
   - ledger_check が落ちたら止めずに続行。冒頭で一行警告し、最後に接続手順を添える

### Phase 1: 全件列挙（`references/enumeration.md`）

```
mcp__zg__gethookd_search_ads
  active_ads_count=1000  technologies=shopify  ads_per_brand_limit=1  limit=50  page=1..11
```
- **`query` を渡さない。** 渡した時点で全件でなくなる
- 538社・約5クレジット・数十秒。結果は zg の research_index で research/banger-index.json に保存し、**次回は差分だけ**
- 課題名を指定された深掘りモードではこのPhaseを飛ばし、Phase 4から入る

### Phase 2: 機械足切り

列挙した538社に、順に機械的なゲートをかける。**この段階では人間の判断を入れない。**

1. **主力商品への広告集中度**（`dropship-check.md` A0）— 上位1〜2商品に7割以上でDS形
2. **サイズ選択で即除外** — `products.json` の `options` に実寸サイズが並ぶもの（靴・衣類・インソール）
3. **剤形で除外** — サプリ・化粧品（日本の薬機法＋製造販売業許可で潰れる）
4. **物流で除外** — バッテリー内蔵・液体・大型
5. **UMゲート**（`same-product-rule.md`）— 「この商品じゃないといけない理由」が物理構造の事実で1行書けるか

### Phase 3: 同一商品クラスタに束ねる

生き残りを**課題ではなく「同一商品」でクラスタに束ねる**（`same-product-rule.md`）。
**束ねる前に必ず実物を見る**（`discipline.md` 1）。`products.json` の `body_html` か商品画像を取得し、
「これは何なのか」を1行書けたものだけをクラスタに入れる。

続けて二次スイープで**分割型オペレーターを合算する**（`enumeration.md` 二次）。
カテゴリ語で `search_brands`（無料）→ `external_id` を着地ドメインで名寄せ → `active_ads` を合算。
これをやらないと Cevera（7ペルソナ合計722本）のような競合を見落とす。

**バンガー基準**（`same-product-rule.md`）で並べ、上位3クラスタだけ深掘りに進める。

### Phase 4: 深掘り（クラスタごとに並列）

**アプリでは別のエージェントを起こせない（Agent ツールが無い）。クラスタを1つずつ、同じ手順で順に深掘りする（長くなる時は next で自分に続きを頼む）。** 各クラスタで守ること:

1. 読むもの: `references/` の discipline.md / scoring.md / dropship-check.md / market-size.md / yakkiho.md / metrics.md
2. 調査項目:
   - **ドロップシップ判定A（商品側5チェック）** — Alibaba/CJの実URL2本以上・原価・MOQ・日本倉庫。×なら即除外
   - **ドロップシップ判定B（競合側）** — 競合ごとに DS型/ハイブリッド/自社ブランド を根拠付きで
   - **市場規模** — `market-size.md`。**「買う人の数」で数える**（悩んでいる人の数ではない）。公的統計の一次資料URL必須
   - 競合各社の active_ads（**Hookdで取る。ブラウザでMetaを1社ずつ開かない**）／訪問数（**決勝3〜5社だけ**・`metrics.md`）／日本空白度／薬機法／物流
   - **ファネル型**（PDP直行 or advertorial/listicle前段、native static比率、DCO利用）
   - **オファー構造とAOV観測**
   - **ユニークメカニズム** — (a)競合の解決側UM実測 (b)自社が取れるUM。**UMが立たなければ判定を1段階下げる**
   - **必須素材**（`report-requirements.md`）: 同一商品の site 3／native 3／advertorial 3／VSL 3／広告アカウントTop3。
     **`search_ads` の返り値に `share_url` `landing_page` `page_type` `days_active` `performance_score` が入っているので、ここから取る**
   - **定点観測**: zg の research_stores（observe:true・ads に {ドメイン: 広告の本数}）→ research/観測.json
3. 返却スキーマ: 結論（判定+スコア）／各軸の実測値+根拠1行／DS判定A・B／市場規模／マージン概算／
   競合表（社名・ドメイン・**実物1行**・DS型か・広告数・継続日数・訪問数+ソース・ファネル型）／トップ広告のshare_url／手動確認ポイント

### Phase 5: 1位だけ確定（**複数返さない**）

**必須7つ（下の「運営者 の最新の決まり」）を満たす商品が無ければ確定しない。** 台帳に見送りとして記録し、Phase 1に戻って次の帯（500-999本）を掘る。
運営者には「まだ見つかっていない。次はここを掘る」と報告する（`discipline.md` 7）。

満たす商品があれば**参入パック**をまとめる。
1. 商品の具体形（Alibaba/CJの実URL・原価→マージン2ルール通過）
2. 参入コンセプト（**問題側UM + 解決側UM=この商品じゃないといけない理由（必須・事実ベース）**／認知レベル／空いているアングル）
3. ファネル型／4. オファー骨子／5. **ec-native-ads スキルへの引き渡しブロック**

### Phase 6: レポート発行（1枚だけ）

zg の product_start で商品フォルダを作り、`references/report-template.html` を実データで埋めて、write_file で `<商品>/00_リサーチ/参入パック.html` に**1枚**保存する（title=「<商品名> 参入パック」）。返事の attach に入れると、アプリの画面で開ける（Artifact は使わない）。
- 競合ブランド名は**必ず実サイトへのリンク**。広告は share_url リンク
- 数字には信頼度ラベル（①実測/②間接/③推定）
- **同一商品として数えなかった競合を、理由付きで別枠に必ず書く**（電動/別剤形/別用途）
- 埋まらない枠は「取得できず＋理由」と赤字で書く。空欄で誤魔化さない
- ランキングページは作らない

### Phase 7: 台帳に書き戻し

1. zg の ledger_record で**今回調べた候補を全部**書く（確定1件＋見送り分。1件ずつか配列）。確定の1件は ledger_claim も。フィールド: `date key niche product score verdict dropship sourcing competitors market note report updated`
2. research_index で research/banger-index.json を更新（測ったものは二度測らない）
3. Hookdの消費クレジット（remaining_credits）を報告


## 確定の判定の決まり（v6 の点数より先に当てる）
`references/確定の判定の決まり.md`。点数を付けず、**必須7つ**（アングル5つ以上／今すぐ痛い／AliExpress にある／ユニークメカニズム＝写真1枚で違いが分かる／単価が低すぎない（1万円前後）／効き目が数日で出る／「原因はそこだった」の角度）と除外（化粧品・口に入れる物・バッテリー・液体・大型）、なるべく（中国から届いても安っぽくない・作りが単純・説明なしで使える）で落とし、残りをアングルの多さで並べる。**Hookd は使わなくてよい**（ウェブ・レビュー・発信で調べる）。判定に使わない：訪問数・利益率・空白度・Amazon で買えるか。
v6 の Phase 1〜3（全件列挙・機械足切り・同一商品）は候補を出す道具として残し、確定の判定はこの7つで行う。

## 出力ルール

- 構成は「結論（1商品）→ ドロップシップ判定 → 市場規模 → 競合エビデンス → 参入コンセプト → 参考広告 → ネクストアクション」
- 取れなかった数字は捏造せず「未取得＋理由」と書く
- **運営者に複数の商品を選ばせない**。1位を出し、2位以下は理由1行
- **必須7つを満たさない商品を成果物として出さない**
